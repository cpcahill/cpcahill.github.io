CyberPower Systems  ·  AI Specialist Intern May – Aug 2025

An agent that audits rebate claims before they get paid

Distributors submit rebate claims against negotiated pricing, and someone in operations checks each one by hand. The failure mode is not a wrong number, it is a duplicate: the same claim submitted twice, months apart, in a slightly different format. Manual review had already caught over $50,000 of false reimbursements in a few months self-reported, which told me the checking was working and the checker was the bottleneck.

What I actually did
Pitched several automation ideas to leadership, then scoped and built the one they picked. Claims arrive in eight different formats. Some are clean Excel exports, some are documents scanned by hand, and each one has its own layout and its own rules for what makes a claim valid. The tool works out which format it is looking at, applies that format's audit logic, and checks every claim against accumulated history to surface duplicates.
The decision I would defend
I split the problem where the two halves actually differ. Recognising which of the eight formats a smudged scan belongs to, and pulling fields out of it, is genuinely hard to specify and a good use of a model. Once the format is known, the pricing and rebate rules are deterministic, so I wrote them as code the operations team can read and correct rather than asking a model to judge. A model that silently approves a claim is worse than no tool at all, because it removes the person who would have caught it.
How it ended
I handed it to the Channel Sales Operations team and the lead technical consultant, walking through how it works, how to run it, and how to change it, so it would outlive the internship. I also sat in on weekly sales and operations meetings as the department's first intern, which is where the actual use cases came from.

Pathfinder  ·  Personal project 2026, ongoing

A job search engine that ranks deterministically and explains itself

The first version did what most of these do: fetch listings, hand them to a language model, ask which ones fit. It produced fluent paragraphs and unreliable answers. The same posting could be a strong match on one run and go unmentioned on the next, and there was no way to audit why.

So I moved the decision out of the model. Listings now pass hard filters first, then score across seven weighted axes. The model writes the commentary, which is what it is good at, and is explicitly told not to reorder the results.

The part worth stealing
Pay is compared after adjusting for local cost of living, so $70,000 in Kansas City outranks $85,000 in San Francisco. A ranking that ignores that is just sorting by a number nobody actually optimizes for.
What I got wrong first
I originally wrote my preferences out as a document and retrieved chunks of it per query. It seemed principled and it quietly lost information: facts needed on every request only appeared when the phrasing happened to retrieve them. RAG is the right call when there is more material than you can fit in a prompt, but my preference sheet is one page, so now I just include the whole thing on every request.

Handshake AI  ·  AI Fellow, contract Jul 2026 – present

Finding the answers that read well and are wrong

I evaluate language model output against task requirements and write structured feedback used to improve model behaviour. The interesting failures are not the obvious ones. They are the responses with clean structure, a confident tone, and a reasoning step that does not hold, which automated metrics score highly and a skimming reader accepts.

It has changed how I build. I now assume a plausible-looking output is the default failure mode, and design so a person can check the reasoning rather than the conclusion. Both projects above are that idea applied.
